1. 두 갈래의 역할

학교에서는 공부에 몰입하고, 모바일에서는 바로 확인하고 처리합니다. 간단한 관리 기능은 모바일 중심으로 옮기되, PC에서도 필요한 순간 열 수 있어야 합니다.

| 현재 기능 | 가상 학교: 아이패드·PC | 모바일: 폰 |
|---|---|---|
| 오늘·할 일·학습 큐·복습 큐 | 등교 화면의 다음 공부 1개 | ‘오늘’ 목록과 바로 이어 풀기 |
| 혼자 풀기·덱 문제·교실 확인 문제 | 과목 교실의 공통 풀이 화면 | 같은 문제를 한 열로 표시 |
| 교실 판서·자막·수업 회차 | 교실 칠판. 필요한 회차·단계 열기 | 같은 내용의 세로 보기 |
| 장·절·학습 경로 | 교실 안 단원 목록 | ‘과목’의 접이식 목록 |
| 시험 대비·시험 범위·지식맵 | 교실의 시험 범위 필터·약점 표시 | 같은 필터와 남은 문제 |
| 교수님 자료·노트·사진·암기노트·제출본 | 교실 책장, 도서관에서 통합 검색 | 과목별 자료 목록·열기 |
| 계획·달력·반복 루틴·예약 | 시간표를 열어 조회·편집 | ‘계획’에서 빠른 확인·편집 |
| LMS 과제·공지·확인 요청 | 게시판. 과제는 다음 공부와 연결 | 오늘 목록·확인함 |
| 타이머·과제 시작/종료 | 풀이 화면의 공통 시간 조작부 | 같은 활동의 시작·중지·종료 |
| 출결·학습 기록·자료 확보율 | 과목 기록부. 각각 구분 | 과목 기록에서 조회·입력 |
| 학점·졸업·과목 평가·규칙·편집 | 상단 ‘관리’에서 필요할 때 열기 | 과목 관리 중심 |
| 개별 질문창·코칭창·우측 패널 | 하단 스앵님 도크 하나 | 축소 도크 하나 |
| 설정·가져오기·내보내기 | 상단 설정 | 설정 |

폰에는 지도 축소판을 기본으로 주지 않습니다. `오늘·과목·계획`을 유지합니다. 학교 링크를 누르면 대응하는 과목·문제로 바로 연결합니다. 기능 접근을 막거나 PC 사용을 강제하지 않습니다.

화면 회전이나 키보드 등장으로 학교와 모바일 모드가 갑자기 바뀌면 안 됩니다. 아이패드 분할 화면에서는 현재 공부를 유지한 채 한 열로 줄입니다.

2. 가상 학교의 공간

첫 학교는 ‘교실동·자습실·도서관’ 세 공간으로 충분합니다. 게시판과 시간표는 학교 안의 공용 설비로 둡니다.

| 공간 | 실제 기능 | 효율에 더하는 것 |
|---|---|---|
| 학교 지도 | 공간 선택 + 오늘 할 것 1개 | 현재 목적지와 다음 행동을 함께 보여줌 |
| 과목 교실 | 장·절별 문제, 수업 회차, 자료, 기록 | 공부 중 필요한 것을 같은 장소에서 해결 |
| 자습실 | 과제·복습을 섞은 오늘의 대기 목록 | 과목을 반복해서 고르지 않고 이어 풀기 |
| 도서관 | 전체 자료 검색. 교실 책장과 같은 원본 | 과목·회차를 모를 때 자료를 찾음 |
| 게시판 | 마감·공지·확인 요청 | 처리할 항목에서 해당 과제·자료로 직행 |
| 시간표 | 기존 계획·루틴·예약 | 다음 공부와 확보 시간을 함께 확인 |

교무실은 만들지 않습니다. 질문하려고 방을 옮기는 것은 도크 하나 원칙과 충돌합니다. 스앵님은 어느 공간에서도 하단에 있습니다.

시험장도 첫 버전에서는 만들지 않습니다. 현재 확인한 시험 대비 기능은 범위·덱 진입입니다. 우선 교실의 ‘시험 범위’로 통합합니다. 별도 시간 제한·답안 제출·결과 검토가 실제로 구현될 때 시험장 분리를 검토합니다.

운동장·매점·기숙사·공사 예정 건물은 두지 않습니다. 자료만 있는 과목도 접근할 수 있게 하되, 없는 문제를 채워진 교실처럼 표현하지 않습니다.

3. 하루 흐름과 화면 수

`학교 → 오늘 이어 풀기 → 교실의 문제 → 필요하면 도크 → 다음 문제 → 오늘 기록`

- 첫 접속: 학교 장면에 다음 공부 1개와 `이어 풀기`를 표시합니다.
- 버튼 한 번으로 해당 교실의 문제를 엽니다. 건물·복도·교실 문을 차례로 누르지 않습니다.
- 교실은 문제부터 시작합니다. 판서 수업은 막힌 단계에서 열거나 직접 선택합니다.
- `힌트` 한 번으로 같은 화면의 도크가 열립니다. 문제·답안·스크롤을 유지합니다.
- 채점 후 `다음`으로 이어 풉니다.
- `오늘 마치기`를 누르면 같은 화면에 학습 기록을 펼칩니다. 저장은 매 행동마다 하며, 하교 버튼에 의존하지 않습니다.

목표는 첫 문제까지 1번, 중단한 문제의 재접속은 자동 복원입니다. 일상 흐름의 전체 화면은 학교와 학습 화면 2개입니다. 도움·기록은 화면 안에서 엽니다.

직접 탐색은 지도에서 과목 문을 누른 뒤 `절 → 문제`를 선택합니다. 과목마다 별도 건물을 만들어 탐색 단계를 늘리지 않습니다.

5. 시각과 제작 방식

정면에 가까운 2D 학교 단면도를 권합니다. 복도와 과목 문이 보이고, 옆에 자습실·도서관이 연결되는 구성입니다. 지도 전체가 한 화면에 들어오게 합니다.

아이소메트릭은 공간감이 좋지만 그림 제작과 작은 터치 영역 처리 비용이 늘어납니다. 카드형 복도는 제작이 쉽지만 기존 목록과 인상이 크게 다르지 않습니다. 2D 단면도가 학교 분위기와 직접 접근을 함께 만들기 좋습니다.

1040×918 기준 제안은 다음과 같습니다.

- 상단 56px: 학교로 돌아가기·현재 과목·확인·관리.
- 본문 718px: 지도 또는 학습 내용.
- 하단 144px: 스앵님 도크 하나.
- 교실은 작은 과목 명패와 칠판 테두리로 장소를 표현합니다.
- 문제를 풀 때 지도·복도·장식은 본문에서 사라집니다.
- 레이저·별도 전신 캐릭터·자동 이동 연출은 없습니다.

Figma 시안은 새 학교 껍데기를 구현하기 전에 필요합니다. 학교, 문제 풀이, 도크 펼침, 폰 화면의 4개 상태면 됩니다. 긴 수식과 실제 문제를 넣어 확인해야 합니다. 이미 진행 중인 풀이 로직 분리는 계속할 수 있습니다.

초안은 Figma 도형·SVG와 기존 스앵님 자산으로 만듭니다. 생성 이미지 없이 구조를 결정할 수 있습니다. 승인된 뒤에도 학교 공통 배경과 반복 가능한 문·책장 부품을 우선합니다. 회차별 배경·동영상·새 캐릭터 제작은 뒤로 둡니다. 이미지 생성 크레딧 잔량과 실제 제작비는 확인 못 했습니다.

아이패드 Safari 성능은 실측 전입니다. 다음을 통과 기준으로 제안합니다.

- 현재 회차만 불러오고, 32회차를 동시에 실행하지 않습니다.
- 지도는 정적 그림과 실제 버튼으로 구성합니다.
- 그림 로딩 실패에도 버튼과 문제는 사용할 수 있어야 합니다.
- 키보드·도크를 펼쳐도 문제와 답 입력창이 가려지지 않아야 합니다.
- 터치 영역은 최소 44×44px로 둡니다.
- 장식 때문에 첫 문제 진입 클릭 수가 늘어나면 수정합니다.

6. 기존 ①~⑦과 합치는 순서

10/19는 요청에서 주어진 보호 기준일로 사용합니다. 실제 캘린더와 개발 가능 시간은 확인하지 않았으므로, 날짜별 완공 약속은 하지 않습니다.

| 단계 | 바뀐 작업 | 통과·복귀 조건 |
|---|---|---|
| ① 문제 은행 | 완료 보고된 625개를 실제 작업본에서 대조. ID·출처·장절·채점 방식 확인 | 기존 문제·기록 연결 유지 |
| ② 공통 풀이 | 한 단원부터 완성. 학교·모바일이 같은 부품 사용 | 답안 저장·재접속·기존 링크 확인 |
| ③ 공통 도크 | 현재 문제 문맥·도움 기록·늦은 답변 분리 | AI 실패에도 풀이 지속, 질문창 하나 |
| ④ 다음 공부 | 진행 중 → 과제 → 약점 복습 순으로 선택 | 미분류·후보 없음 처리. 화면의 첫 버튼 탐색 제거 |
| ⑤ 두 갈래 껍데기 | Figma 시안 후 학교와 모바일 진입 구성 | 설정 한 번으로 옛 화면 복귀 |
| ⑥ 범위 확장 | 덱·32회차를 공통 화면에 연결. 원본 템플릿·생성기도 함께 수정 | 미전환 회차는 기존 화면으로 연결 |

시험 전에는 ①~④와 검증된 한 단원의 학교 시범을 우선합니다. ⑤~⑦의 전체 전환은 시험 기간 이후로 넘기는 것을 권합니다. 10/19 직후에도 다른 시험이 남을 수 있으므로 그날을 전체 전환일로 잡지 않습니다.

되돌리기는 화면만 복원해서는 부족합니다. 새 화면에서 푼 기록을 옛 화면도 읽어야 합니다. 기존 ID와 저장 형식을 보존하고, 새 필드는 호환 가능한 추가로 제한합니다. 그 호환성을 확인하지 못하면 새 화면은 기본 진입으로 올리지 않습니다.

7. 반대 의견과 실제 위험

- ‘심플한 기능을 모두 폰으로’라는 지시를 기능 삭제로 적용하는 데 반대합니다. 아이패드에서 공부하다 마감·자료·계획을 보려고 폰을 찾아야 하면 효율이 떨어집니다. 관리 화면을 학교의 주 화면에서 빼고 보조 접근은 남깁니다.

- 학교와 모바일을 따로 개발하면 기록·채점·도움 사용 기준이 갈라집니다. 공통 풀이와 저장 처리를 먼저 완성해야 합니다.
- `realm.js`를 그대로 복제하는 데 반대합니다. [현재 파일](</C:/Users/user/본사/atom/kingdom/realm.js:5>)은 `REALM_OFF = true`로 비활성화돼 있습니다. 공사 예정 건물도 포함합니다. 공간 진입 발상만 참고합니다.
